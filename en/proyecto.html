Data Pipeline for Historical BTC Arbitrage Analysis

This data engineering project reconstructs historical Bitcoin price spreads between Binance (BTC-USDT) and Buda.com (BTC-CLP), adjusting for the USD/CLP exchange rate.

The AWS pipeline combines one-minute Bitcoin market data with daily USD/CLP exchange rates from Chile’s central bank. It normalizes the data into a unified Silver layer in Parquet and exposes it through Athena, where partition projection helps control query costs. The demo query identifies sustained Buda premiums of at least 1% across nine years of data.

Results

The analysis identified 34 hours of significant arbitrage opportunities across nearly nine years of data, from August 2017 through April 2026. An episode qualified if it met both criteria.

  • Persistence. The price difference lasted more than five consecutive minutes, reducing the influence of brief anomalies or temporary drops in liquidity.
  • Profitability. Buda traded more than 1% above Binance, the minimum threshold used to account for operating costs, exchange fees, and the daily exchange rate.

What the Pipeline Measures

Chilean exchanges such as Buda.com may trade at sustained premiums to the international BTC market because of low liquidity, currency conversion friction, and operational barriers to arbitrage. This project builds the historical dataset needed to measure those spreads minute by minute from 2017 onward.

The pipeline ingests three sources with different schemas, normalizes them in a shared Silver layer, and produces aligned time series for analysis. The portfolio project demonstrates batch pipeline design on AWS, with an emphasis on idempotency, observability, and explicit engineering trade-offs.

Running the Pipeline

Prerequisites

  • AWS CLI with credentials configured
  • Terraform >= 1.5
  • Python 3.11+
  • zip, unzip, and bash on your PATH

Deploy the Infrastructure

cd infra/
terraform init
terraform apply

Terraform creates the S3 bucket btc-arbitrage-data-lake-001, the ingestion Lambda functions (fetch-binance, fetch-buda, fetch-mindicador) and transformation functions (silver-buda, silver-binance, silver-fx), the ingestion state machines for each source, a Glue catalog with partition projection, an Athena workgroup with a 200 MB scan limit, an Athena results bucket with a seven-day lifecycle, and the corresponding IAM roles.

Package the Lambda Functions

./build_lambdas.sh                      # Package all Lambda functions
./build_lambdas.sh <lambda_name>        # Package a single Lambda function

The build script uses an explicit allowlist of .py files and creates reproducible archives with zip -X, keeping Terraform’s source_code_hash stable when the code stays the same. Functions in LAMBDAS_NEEDING_COMMON (silver_binance and silver_fx) also bundle the lambdas/common/ module.

Backfill Historical Data

Binance (concurrency of 3, about 7.5 min for nine years):

python scripts/generate_backfill_periods.py > backfill_input.json

aws stepfunctions start-execution \
  --state-machine-arn $(cd infra && terraform output -raw state_machine_arn) \
  --input file://backfill_input.json

Buda (concurrency of 1, about 10 h for eleven years):

python scripts/sample_buda_monthly_volume.py > buda_monthly_volume_sampled.json
python scripts/generate_buda_periods.py > backfill_buda_input.json

aws stepfunctions start-execution \
  --state-machine-arn $(cd infra && terraform output -raw buda_state_machine_arn) \
  --input file://backfill_buda_input.json \
  --name "buda-backfill-$(date +%Y%m%d-%H%M%S)"

The Buda backfill runs serially (MaxConcurrency = 1) to stay within the exchange’s rate limit. Run the backfill in yearly batches.

Backfill USD/CLP Data (Mindicador.cl)

One invocation writes one file in about six seconds.

aws stepfunctions start-execution \
  --state-machine-arn $(cd infra && terraform output -raw mindicador_state_machine_arn) \
  --input '{}'

Each run downloads the entire series from 2015 onward and produces the same result given the same data. The resulting Bronze file is about 107 KB.

Process the Silver Layer (Bronze → Silver)

Invoke all three Silver Lambda functions manually. Each run reprocesses all Bronze data in an idempotent full refresh with no intermediate state.

# Silver Buda rebuilds OHLCV from trades (~48 s, 5.83M candlesticks, 134 partitions)
aws lambda invoke \
  --function-name silver-buda \
  --invocation-type RequestResponse \
  --cli-read-timeout 300 \
  /tmp/silver_buda_response.json

# Silver Binance casts values and joins FX (USDT to CLP, ~97 s, 4.58M candlesticks, 105 partitions)
aws lambda invoke \
  --function-name silver-binance \
  --invocation-type RequestResponse \
  --cli-read-timeout 300 \
  /tmp/silver_binance_response.json

# Silver FX forward-fills holidays (~6 s, single file)
aws lambda invoke \
  --function-name silver-fx \
  --invocation-type RequestResponse \
  /tmp/silver_fx_response.json

Each JSON response includes execution metrics for processed rows, the percentage of interpolated or forward-filled rows, and peak memory usage.

Analyze the Data in Athena

The demo query (infra/athena_queries/spread_episodes.sql) identifies periods when Buda sustained a premium of at least 1% over Binance. See the Results section for the findings.

# Run the query
QID=$(aws athena start-query-execution \
  --region us-east-2 \
  --work-group arbitraje_btc_wg \
  --query-string "$(cat infra/athena_queries/spread_episodes.sql)" \
  --query-execution-context Database=arbitraje_btc \
  --query 'QueryExecutionId' \
  --output text)

# Wait and retrieve results (scans ~125 MB in ~3 seconds)
sleep 5
aws s3 cp s3://btc-arbitrage-athena-results-001/queries/${QID}.csv query_results/resultado_arbitraje.csv

The arbitraje_btc_wg workgroup caps each query at 200 MB to prevent accidental full-table scans, which would read several GB without filters.

Architecture Decisions

Five decisions shaped the pipeline.

1. Binance Endpoint data-api.binance.vision

The api.binance.com endpoint returned HTTP 451 for AWS IP addresses in U.S. regions, including us-east-2, because of regulatory restrictions on requests from U.S. IP addresses.

The public data-api.binance.vision subdomain exposed the same market data schema without that geographic restriction. We diagnosed the issue by logging the outbound IP address at handler startup and adopted the practice in both handlers.

2. Preserve Raw Data in Bronze and Deduplicate in Silver

Both Lambda functions store raw API responses, including expected overlaps caused by pagination. Binance uses an inclusive endTime, while Buda uses an exclusive cursor. Silver handles cleanup in Parquet under a unified schema.

We accept fewer than 0.003% duplicate records in Bronze so we can reprocess the data without calling the APIs again.

3. Adaptive Batching Based on Observed Volume (Buda)

Binance uses one file per month. For Buda, the generator (generate_buda_periods.py) samples trade volume on the 15th and splits the month into one, two, or four to five files. It estimates Lambda wall-clock time from the sample and adjusts the batch size to leave room below the 900-second timeout.

The heuristic misses months with short bursts of activity. During the December 24–31, 2020 BTC rally, the quiet sample on the 15th underestimated the month’s volume. We used targeted overrides with batches shorter than a week for the affected half-months.

4. Tune Throttling with Runtime Metrics

The Buda handler writes runtime metrics to each Bronze file (wall_clock_seconds, effective_rps, nominal_rps, and throttle_429_events). Those measurements supported reducing BUDA_THROTTLE_SECONDS in stages, from 3.0 to 2.0 to 1.0 seconds.

Across 247 runs, none triggered throttling. The shorter delay would substantially reduce future backfill times for other Buda pairs such as ETH-CLP and LTC-CLP.

5. Describe Data in Silver and Apply Filters in Gold

The Silver layer keeps outliers, unusual candlesticks, and atypical volumes. It records lineage flags (is_interpolated and is_ffilled) and warns about invalid values (close ≤ 0 or volume < 0). Outliers can be the signal in arbitrage analysis, so the pipeline preserves them and leaves filtering decisions to analytical queries.

Each Silver Lambda reprocesses all Bronze data on every invocation. The same Bronze data and code produce the same Silver output, with no intermediate state, partition checkpoints, or deltas to reconcile. At the current volume of 10.4 million candlesticks in under two minutes, the cost is low.

The catalog uses partition projection to infer unified_candles partitions from a declarative formula (years 2017–2026 and months 01–12). Terraform defines the entire catalog, which eliminates the need to update Glue partitions with MSCK REPAIR TABLE or ALTER TABLE ADD PARTITION after a Silver refresh. The demo query scans 125 MB across nine years in about three seconds. The workgroup stops queries that scan more than 200 MB.

  • Lambda with pagination, idempotency, and rate-limit handling
  • Step Functions orchestration of 112 monthly invocations with a concurrency of 3
  • About 4.5 million klines in an S3 data lake with Hive partitioning

Phase A.2 · Buda Historical Ingestion (Complete)

  • Reverse pagination using an exclusive cursor
  • Adaptive batch sizing based on observed volumes
  • Runtime metrics in metadata for tuning throttling
  • Backfill from 2015 to 2026 with end-to-end validation of zero gaps or overlaps

Phase A.3 · USD/CLP Exchange Rate (Complete)

  • Handler for MIndicador.cl
  • Forward-fill for weekends and Chilean holidays, covering the full operating range with gaps of up to seven days

Phase A.4 · Silver Layer and Athena Queries (Complete)

  • One-minute OHLCV reconstruction from Buda trades
  • FX join to normalize Binance prices from USDT to CLP
  • Unified unified_candles schema with 11 columns, partitioned by year and month
  • FX forward-filling and lineage flags (is_interpolated, is_ffilled)
  • Glue Data Catalog with partition projection
  • Athena workgroup with a 200 MB scan limit
  • Demo query for sustained Buda premiums over Binance

Phase A.5 · Materialized Gold (Outside V1 Scope)

At the current data volume and query frequency, Athena runs analytical queries directly against Silver in about three seconds. A materialized Gold layer remains a future phase for frequent queries or a downstream consumer, such as a dashboard or API, that would justify the maintenance cost.

Lessons Learned

  • Geographic restrictions can be hard to diagnose. An HTTP 451 response from Lambda in us-east-2 prompted us to investigate binance.com. News reports about the block led us to switch to the public market data subdomain. Logging the outbound IP address at startup saved hours of debugging and became standard in both handlers.
  • Parallelizing the work delivered the biggest speedup. Step Functions ran three Binance batches concurrently and cut the backfill from about a day with a sequential script to 7.5 minutes using the same handler.
  • Measure before tuning. We adjusted the Buda throttle using per-run metrics such as effective_rps and wall_clock. After 92 runs at 3.0 seconds with zero 429 responses, we had enough evidence to try 2.0 seconds.
  • A single sample misses concentrated spikes. Sampling the 15th works for months with steady volume but underestimates activity around events such as the December 24–31, 2020 rally and the May 19, 2021 flash crash. Targeted overrides handled those cases while keeping the general batching rule simple.
  • Raw Bronze data makes cleanup repeatable. By documenting pagination overlaps and deduplicating in Silver, we can change the cleanup logic and rerun it without hitting the APIs again. The small cost of deduplication buys idempotent reprocessing.
  • Tune the system where it fails. Twice during the Buda backfill, a failure made it tempting to chain Lambda functions or add a scheduler. In both cases, tuning a parameter solved the issue with the existing architecture. See Gall's Law.

Limitations

The project demonstrates data engineering in a portfolio. Its design choices affect how the results should be interpreted and how the pipeline can be used.

  • Filtering interpolated candlesticks introduces selection bias. Buda candlesticks with is_interpolated = true represent minutes with no trades (about 81% of the total). Their prices come from the last known trade. The demo query excludes those minutes and reports spreads when Buda actually traded. Those minutes may coincide with higher market activity and wider spreads.
  • Queries run directly against Silver. Athena returns exploratory results in about three seconds across nine years of data. Frequent or subsecond queries from an interactive dashboard or public API could justify pre-aggregated Gold tables.
  • Reported spreads are theoretical. The metrics use closing prices (close_clp) and omit order book liquidity and market depth. At a 5% spread, the available trade size matters whether it is 0.1 BTC or 10 BTC. The query also omits per-episode fees (about 0.1% on Binance and 0.4–0.8% on Buda, plus transfer costs). The 1% threshold serves as an estimate of minimum costs.
  • Validation is manual. The project includes validation scripts (verify_bronze_coverage.py and benchmark_mindicador.py). We manually checked the FX time zone, the distribution of gaps, and the silver-binance out-of-memory issue. Formal unit and integration tests in CI would be the first priority before regular use.
